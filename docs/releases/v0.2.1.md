# Arelis v0.2.1 — patch notes

Released 17 Aug 2026. Twenty-two items, built over one sitting, in the order
they are listed.

Checkout data stays in the repo. Installed profile stays
`%LOCALAPPDATA%\Arelis`. This release does not copy one into the other.

---

## In this patch (order we built it)

1. **User data lives with the account.** Checkout uses the repo. Installed
   Arelis uses `%LOCALAPPDATA%\Arelis`. `ARELIS_DATA_DIR` still wins. An
   update must not write into Program Files or share one book across users.

2. **Weather tool.** Forecast for *your* place via Open-Meteo. The model
   cannot pass invented coordinates and wander to the wrong city.

3. **Contacts book.** You add people in the UI. Handle, aliases, mobile.
   Arelis does not invent contacts. Tool + YAML store.

4. **Contacts plate.** Floating glass address book (View → contacts / Ctrl+6).
   Not a dock, not tabbed with history. Always opens on the list. Save stays
   on the card. Stack pages are opaque so the list cannot ghost through.

5. **Notifications mailbox.** Floating inbox for texts, calendar, mail, jobs
   while Arelis is open. Pill + card stay. Inbound texts do not dump into
   the main chat.

6. **SMS / mail / calendar routing.** Draft complete for “text wife: …”,
   email, and agenda. Fail tags nudge a replan when scrape/search/send/image
   miss. Plan nudges for research / weather / send. SMS hide-image wander
   stays off.

7. **Wake is “Hey Arelis” only.** Bare name does not wake. Whisper spelling
   list (`arrelis`, `Pay a relus` at clip start, …). No Whisper
   `initial_prompt` on wake clips. Receipt: conversation icon latches, orbit
   says listening. Every decision hits `logs/voice.log`.

8. **Voice models can fall back.** Checkout with an empty `models\` can use
   weights already in the installed profile.

9. **SMS chat tiles.** Open a person from a text notice (double-click or
   Open as chat). One glass room per person. You type, Enter sends a real
    text — no Allow card (you are not the model). Session-only bubbles.
    Agent “text wife: …” from conversation still uses Allow. Soft cap 8.

    Fixed while auditing: no tile could be built at all. `SmsChatWindow` armed
    the heading's event filter mid-construction, `root.addLayout(head)`
    reparented that label, and Qt ran the filter — whose first line reads
    `self.input`, eighteen lines before it exists. `AttributeError` out of
    `__init__`, up through `registry.open()`, into the double-click slot, where
    PySide prints a traceback and the click appears to do nothing. Both filters
    are now armed at the end of `__init__`. Five tests in
    `tests/test_sms_chat.py` were failing on this.

10. **Glass plates are opaque and round.** Contacts was see-through (layered
    HWND). Notifications had a black square (opaque rect behind a rounded
    paint). Same seal as the main window: opaque fill + rounded mask.
    Settings and SMS tiles use it too.

11. **One surface owns the moment.** Visible chat tile swallows that person’s
    pill, inbox unread, and voice. Unfocused tile: warm amber rim breath,
    then a steady ember, until you click it. Minimized tile: doorbell as
    before. Notifications inbox open: pill and max chip hide.

12. **Cold launch is a new chat.** Empty orbit, “what are we working on.”
    Last night stays in History. Tray / un-minimize do not start a new
    conversation. Unused empty shells from a short launch are pruned. CLI
    still continues the last real thread.

13. **Contacts is one layer of glass.** The people list *and* the card are
    holes in the plate, same as the notifications inbox.

    The Save-ghost was never the hidden list compositing. Those containers
    carried `WA_OpaquePaintEvent`, and Qt paints neither the palette fill nor
    the stylesheet background for a widget with that attribute, while also
    refusing to repaint the plate underneath it. A plain `QWidget` /
    `QStackedWidget` / `QScrollArea` therefore painted *nothing* and the
    previous frame stayed in the backing store — the list row behind the
    heading, a second Save button, a blurred hint, all of it surviving a
    window drag. Save made it obvious only because Save is what relayouts the
    card (heading text, hint shrinking to “Saved.”).

    Gone: `_see_glass`, `_seal_opaque`, `_glass_or_solid`, the `solid` Qt
    property and its `#Contacts*[solid="true"]` rules, and the manual
    page-visibility loop. Colour comes from the stylesheet only;
    `QStackedWidget` hides the page it is not showing and hidden widgets do
    not paint. `tests/test_contacts_panel.py` now guards the invariant: no
    contacts container may set `WA_OpaquePaintEvent`.

    Rule for the rest of the app: `WA_OpaquePaintEvent` belongs only on a
    widget with a real `paintEvent` that fills its whole rect (`GlassFrame`
    at `fill_alpha >= 240`). Never on a container you colour with a
    stylesheet.

14. **Audit of the never-audited core.** `sms_complete`, `fail_tags`,
    `plan_nudge`, `agent_loop`, `wake`, `stt`, `voice/telemetry`,
    `memory/store.start_glass_session`, both weather modules and
    `contacts_tool`, read end to end — `agent_loop` by structure plus sampled
    windows, because it is too large to read whole. Two things were wrong
    enough to fix tonight.

    *The cold-launch prune could delete a real conversation.*
    `start_glass_session` deleted the newest session whenever it was not also
    the newest session *with messages*, and never re-checked that it was
    actually empty. `_utc_now()` truncates to the second and
    `latest_session_id` had no tiebreak, so two conversations opened inside the
    same second are ordered arbitrarily — and the two lookups are different
    queries, one carrying an `EXISTS` subquery, so they can break that tie
    differently. When they do, the "leftover shell" is a thread with messages
    and `delete_session` cascades them away. The existing test in
    `tests/test_memory_store.py` creates both of its sessions inside the same
    second, so it was passing on the query planner being consistent rather than
    on the code being safe. Sessions now order by `started_at DESC, rowid DESC`,
    and the prune re-checks the shell for messages before deleting it. A new
    test forces the two lookups to disagree.

    *The first "Hey Arelis" after launch loaded Whisper mid-clip.* Wake
    resolves to faster-whisper while turns run on Sherpa, but `preload()`
    warmed one backend and returned as soon as `loaded()` said yes — and
    `loaded()` reports the turn backend. Sherpa went warm, Whisper stayed cold,
    and the first wake clip paid the load inside the STT lock with no status,
    because the "Loading the speech model" notice asks the turn backend too.
    `_ensure_active` now warms every backend the session will use. Nothing is
    loaded that the first wake clip would not have loaded anyway; the cost
    moved to launch, which is where `preload` exists to put it.

15. **The workspace editor could lose your work without saying anything.**
    Three different things replaced the editor buffer and all three did it
    unconditionally: the operator opening a file, Arelis writing one
    (`app.py`'s `TOOL_RESULT` branch re-read the file and pushed it in), and a
    save flushing the buffer back to disk. The editor is a plain
    `QPlainTextEdit` with no undo across loads and no autosave behind it, so a
    replacement is final. Type into a file for ten minutes, ask her to touch it,
    and the ten minutes were gone — no prompt, no marker, nothing on screen to
    suggest anything had happened. The same hole ran the other way: her write
    landed on disk, then a save flushed a buffer loaded *before* it and silently
    reverted her.

    The rule now is not "refuse", it is "never silently", because every one of
    those three replacements is legitimate in the case it was written for.

    - The panel tracks dirty by comparing the buffer against the text it was
      last loaded or saved with, rather than latching a flag, so
      `setPlainText()` firing `textChanged` cannot mark a fresh file as edited.
      "unsaved changes" shows at the right of the roots row.
    - `set_file()` returns `False` instead of replacing a dirty buffer, and the
      tool-result path says so in chat: her write is on disk, the operator's
      version is untouched, opening the file again gets hers.
    - Open over unsaved edits and save over a file that changed on disk each
      warn once and then obey on the second press — armed per path, so
      confirming a discard into one file does not pre-approve the next.
      `_disk_moved_under_editor` only fires for the file the editor is actually
      holding, so ordinary saves are never questioned.

    `tests/test_workspace_editor_clobber.py` pins all of it, including the two
    false positives that would make the feature feel broken.

16. **Two loose ends from the earlier items, both caught by existing guards.**
    `tests/test_egress.py` was failing on `geocoding-api.open-meteo.com`, added
    by `briefing/weather.py` and never registered. The guard did its job — the
    host is now on the allowlist with the reason (same keyless provider as
    `api.open-meteo.com`, reached only when the profile names a city and gives
    no coordinates, and sent that city name and nothing else). And the stale
    composer test from the item 14 audit is resolved the way that note asked:
    `panels/conversation.py:204` now sets the same "message Arelis…" the first
    `_sync_composer_buttons()` would have overwritten it with, so there is no
    phantom copy, and the test asserts the resting state that actually exists.
    Full suite: 1,545 passed, 1 skipped, nothing failing.

17. **Rooms.** A named place to work on one thing, with its own conversation.

    The general thread is deliberately forgettable — cold launch is an empty
    orbit and last night is in History (item 12). That is right for "what's the
    weather" and wrong for a three-week analysis, which needs somewhere that
    remembers where it got to and already knows which folder it lives in. A
    room is that place. See [docs/rooms.md](../rooms.md) for the whole surface.

    Four things, and only the last one is load-bearing:

    - **purpose** — plain language, handed to her at the top of every turn in
      the room (`agent_loop.py`, after the project line and before the profile:
      narrower context, deeper in).
    - **root** — the workspace project. Entering makes it active, so a bare
      path lands where the work is.
    - **kind** — `general | code | analysis | research | writing`. Sets the
      model chip and the skill lean.
    - **thread** — its own conversation, resumed on entry. Without this a room
      is a system prompt with extra steps.

    Ways in: `/room <name>`, or say "let's work on physics". Ways out:
    `/leave`, "leave the room", or the button on the strip. Made by
    `/room new`, or by asking — the `rooms` tool lets her build a configured
    room from one sentence, behind an Allow card like every other write.

    Four decisions worth writing down, because each one had an obvious wrong
    answer:

    *Rooms lean, they do not cage.* A tool allowlist per room is the obvious
    design. It is wrong by default: ask the time in the physics room and a
    caged agent has to refuse, which teaches you to stop asking it things. A
    room changes what she reaches for first and nothing else, unless the file
    names `tools:` explicitly — and a `tools:` list matching nothing real is
    ignored, since that is a typo far more often than a request for a room
    where nothing works.

    *Spoken navigation resolves before it acts.* "Let's work on the budget"
    with no budget room is an ordinary sentence and stays one. The pattern is
    only half the gate; the name still has to be a room that exists. The case
    that pins it is `open the file physics.py`, which starts with a verb the
    pattern knows and has to lose.

    *The active room does not survive a launch.* Definitions and threads
    persist; being *in* one does not. Resuming silently would mean a launch
    with three-week-old context, a different model and a different write target
    already active — a mode you did not choose and cannot see.

    *The tool cannot enter a room.* It runs inside a turn that is using the
    thread a swap would replace. Entering is a command, checked against the
    running turn the way a session load already is. The tool creates and
    configures, then says how to walk in.

    Two bugs came out of building it. `MemoryStore.start_glass_session` would
    have pruned a room's thread the moment you made a room and said nothing —
    the newest empty shell is exactly what a fresh room thread is. Both lookups
    are now scoped to general conversations. And `Orchestrator.__init__` had
    `config.get("_rooms") or RoomStore()`, which quietly built a second store
    whenever the shared one was empty — that is, on every first launch — so the
    tool and the loop would have been looking at different objects. `RoomStore`
    defines `__len__`; empty is falsy. Explicit `is not None` now.

    Schema v10 adds `sessions.room_id` (empty string is general, since every
    existing archive predates rooms and a NULL would conflate "general" with
    "unknown"). New: `arelis/rooms.py`, `arelis/tools/rooms_tool.py`,
    `arelis/ui/panels/room.py`, `data/rooms.example.yaml`, `docs/rooms.md`, and
    the `rooms` skill card. Tests in `test_rooms.py`, `test_rooms_flow.py`,
    `test_rooms_agent.py`, `test_rooms_tool.py`, `test_rooms_ui.py`.

    **Verified by driving the real thing.** `scripts/rooms_smoke.py` boots the
    actual window, the actual bus on its own thread, the actual orchestrator and
    archive, and then types into the actual composer — seventeen steps, a
    screenshot of the window after each one, measured state in `steps.jsonl`,
    and a `report.md` tying them together, all under `logs/rooms-smoke/`. It
    runs against a scratch `ARELIS_DATA_DIR`, so the live archive is untouched,
    and stubs only the router, since no room command reaches a model.

    It earned its keep immediately by finding three things the unit tests could
    not, because all three live between layers:

    - `/room set purpose` wrote to disk without republishing `ROOM_CHANGED`, so
      the strip — the only place the purpose and folder are visible — kept
      describing the old room. It looked exactly like the command had not
      worked. Now repainted, and pinned by a test.
    - The reply on entering a room ran `.capitalize()` over the whole sentence,
      which lowercases everything after the first letter and turned the project
      `Arelis Source` into `arelis source`. A project name is a path component,
      so its case is not cosmetic. Also pinned.
    - A false alarm worth recording: the leave button appeared dead. It was the
      harness waiting a fixed second while the window's startup readiness probe
      still had the bus. The harness now waits on the round trip and records how
      long each step actually took, which is why that step now passes honestly
      rather than by having its timeout raised.

    One more found by writing the manual test plan rather than by running
    anything: `/room set kind` saved the new lean but did not apply it, because
    the role is applied on entry — so setting it from inside a room did nothing
    until you left and came back, which reads as the command being ignored.

    Full suite: 1,619 passed, 1 skipped. Smoke run: 17/17 clean.

- What item 15 does *not* do. There is no file watcher, so a change Arelis makes

  then rather than when it happened. There is no diff and no merge: the choices
  are keep mine or load hers, whole file. And the warnings are chat lines, which

  conflict. All three want the review surface, not more gates.

- `panels/conversation.py:475` sizes the resting composer against the width of
  "what are we working on" while the placeholder now reads "message Arelis…".
  Reserves more width than it paints. Left alone because correcting it visibly

- What Rooms v1 does not have yet, in the order they will be missed. There is
  no room picker in the UI — you type or say the name, and `/rooms` is the only
  list. History does not group by room, so a room's threads are mixed in with
  everything else even though the rows now carry the room id. A room cannot
  hold more than one project root. And she cannot run anything in a room; the
  execution-with-review-gates idea is a patch of its own, not a corner of this
  one.

- `panels/workspace.py` lists a directory with a synchronous `cwd.iterdir()`
  (`:289`) on the Qt thread. Capped at 500 entries, so it is fine on a local
  disk and not fine on a network root or a cold external drive — the window
  simply stops painting until it returns.

- `_launch_log_path()` (`tools/comfy_lifecycle.py:190`) writes

  fallback at `:121`.

## 18. She could not change a picture, and could not see a screenshot

Found by a real request, which is the only reason it was found. A friend sent a
game screenshot: *"make this more vibrant and resize it to the correct size for a
YouTube thumbnail."* That went into Arelis verbatim, with the image attached, and
three minutes and three Allow cards later she refused — the last words on screen
being that the calculator only does arithmetic, not symbolic calculus.

Nothing in that turn was a coding mistake. Every tool did exactly what it was
built to do, and the request had no tool that could do it:

- `vision` was called first, because the attachment block routes every image to
  it. Vision can only look, so answering an instruction with it is a category
  error before you get to whether it worked. **It did not work either:** the
  screenshot was 2560x1440 and 7 MB, and Ollama counts an image against the same
  context window as the text, so at full size it came to 4,151 tokens against a
  4,096 window and was rejected with a 400 before the model saw a pixel. Vision
  has therefore never worked on an ordinary screenshot. Nobody noticed because
  the tool reported "Vision failed" and the turn carried on.
- `image` was called next, and *succeeded*, which was worse than failing. It
  generates pixels from a text prompt, so it produced a brand-new picture at
  1280x720 with no relationship to the file — sixty seconds of GPU time spent
  inventing something nobody asked for. The width and height arguments made it
  look like the resize tool it is not.
- `calculator` was forced in at the end by the exactness gate, because
  `_MATH_PATTERNS` treats `N x N` as multiplication. The guard against this
  existed and its comment says so — *"spaces required so image dims (1965x1106)
  never match"* — but "1280 x 720 pixels" is how a person writes a size, and the
  spaces defeated it. She dutifully called `calculator(expression="1280, 720")`,
  which is not an expression, and refused on the failure.

**The tool that should have existed.** `tools/image_edit.py`: resize, crop and
adjust an image that already exists. No model, no GPU, no network — resizing and
saturation are arithmetic on pixels with an exactly right answer, so Pillow does
it in-process in milliseconds. Sizes come as `width`+`height` or a named preset
(`youtube_thumbnail` is 1280x720), and `vibrance`/`contrast`/`brightness`/
`sharpness` take a factor where 1.0 is unchanged and 1.3 is noticeably more.

Three decisions worth naming. It **never modifies the source**, because the input
is usually the only copy of something somebody sent you; every edit is a new file
in `outputs/images/`, named for what happened to it
(`paste-030544-1280x720-vibrant.png`). A shape mismatch is **centre-cropped by
default and the reply says so**, since centre is the only defensible guess when
you do not know what the subject is, and a guess you can see is one you can argue
with — `fit=contain` pads instead. And factors are **clamped to 0.1–3.0**: a
model that decides vibrance should be 40 gets a picture back, not a solid colour
field, because a tool should not have a way to be asked for nonsense and comply.

**The vision fix, which matters more.** `tools/image_io.py` now downscales to a
1024px long edge before encoding. The screenshot that used to 400 goes as 193 KB
instead of 7 MB and answers correctly. Measured on qwen2.5vl:3b, the picture
alone: 1024px is 1,100 tokens, 1280px is 1,221, 1600px is 1,849 — all three
answer, so 1024 is chosen for the margin it leaves the question and the reply,
not because anything above it breaks. `tools.vision.max_edge` is the knob. Two
500s during that measurement turned out to be Ollama connection resets from the
`keep_alive=0` unload racing the next load, not size limits — an unrelated
flakiness worth knowing about, since a second vision call in one turn can hit it.

That same module fixes a second thing quietly. Resolving an image asked the
workspace and then allowed `outputs/images/` — but a pasted attachment is staged
under `data/drops/`, which sits under the *data* root. From a checkout the data
root and the workspace root are the same directory, so this looked correct for as
long as it has existed; **on an installed copy they are `%LOCALAPPDATA%\Arelis`
and `Documents\Arelis`, and every paste would have failed** with "outside
workspace roots" the first time anyone tried it in the shipped product. Reading
from Arelis's own drop and output folders is not an escape from the sandbox, so
both are named as places a picture may come from.

**And the routing, so she picks it.** `attachments.route_tool` sends an image
whose ask is an *instruction* — resize, crop, vibrant, brighter, thumbnail, a
bare `1280 x 720` — to `image_edit` rather than `vision`, and the rules block
names the three wrong tools explicitly, because all three were tried. The agent
loop's finish-after-`image` shortcut now covers `image_edit` too, using the
tool's own sentence as the reply: the round after a finished edit is exactly
where she reached for vision to check her own work and the calculator to verify
the pixel count. `detect_math_ask` no longer forces the calculator when `N x N`
is the only arithmetic shape and the sentence is about a picture; `what is 17 x
19` still does.

Pillow becomes a core dependency rather than an extra, because without it a
pasted screenshot cannot be looked at, which is not a niche.

New: `tests/test_image_edit.py` (22), `tests/test_image_io.py` (12), plus
regressions in `test_attachments.py` and `test_exactness.py` — the spaced
resolution among them, sitting directly beneath the unspaced test whose guard it
broke. Full suite: 1,652 passed, 1 skipped.

Not done: no rotate or flip, no text or overlays, no batch, and no undo beyond
the original being untouched. Iterating ("more than that") means another Allow
card each time, which is the right weight for writing a file and the wrong one
for turning a dial.

## 19. It looked like bronze, and it kept opening Windows dialogs

Two complaints that turned out to be the same complaint. The owner's words were
"everything looks a bit bronze more than amber — think Edison bulbs, evening
lamp, camp fire," and separately that the delete prompts "look like a different
program." Both are the app failing to hold one idea about what it is made of.

**Why it read as metal.** The accent was never the problem: `#ffb457` is a good
amber and it stayed. The problem was everything the accent was sitting next to.
The dim ramp ran `#d4b892`, `#8a7e70`, `#4a4238` — hue 30 at fifteen to thirty
per cent saturation, which is the definition of a warm grey. Put a saturated
orange on a warm grey and the grey does not read as shadow; it reads as the
unlit side of a metal object, and the orange becomes a highlight on it. That is
bronze. The plate gradient opened on `QColor(38, 26, 16)` and did the same thing
one layer down, and the muted text was `rgba(243, 236, 224, N)` — an ivory that
is very nearly neutral, and which composites over black to grey, which is how
the idle prompt ended up looking olive.

The fix was to stop picking colours and pick a light instead: one incandescent
source at roughly 2300K in an unlit room, and every token a reading off it. Two
rules follow from that and they are what the palette is actually built on. The
first is that **darker means redder**, because that is what a cooling ember
does — hue runs from about 33 at the accent down to 17 in the deepest fills,
where the old palette held 30 all the way down. The second is that **saturation
does not fall off in the dark**. A twenty-per-cent-saturated shadow is grey
paint with a tint on it. The new backgrounds sit near black but carry a real
red bias (`#0c0705`, `#140c08`, `#1e120b`), and the mid fills are saturated
enough to be light rather than material.

The tokens the audit asked for are all there and doing work: `hint` for the
secondary prose that was a literal `#d4b892` in six places, `panel_fill` and
`tab_selected` for the two surfaces that were raw `rgb()` triples, a `warn` in
the amber family instead of the off-hue one, and named alphas — `text_soft`,
`text_muted`, `text_faint` — for the type that sits *in* the bloom rather than
on a plate, tinted at the base so it does not composite to grey. Contrast was
checked rather than assumed; body text is over 7:1 on the panel fill and the
dim ramp stays above 2.5:1, and there is now a test that asserts the light model
(red above green above blue, hue under 45, monotonically brighter, contrast
floors) instead of asserting the hexes, so the next retune does not have to
argue with it.

Colour also stopped living in eleven files. The orbit, the plate gradients, the
window atmosphere, the drawn icons, the markdown code blocks and the transcript
bubbles all had their own copies of `255, 180, 87` and their own dark browns;
they read off tokens now, and a second test walks every colour the stylesheet
emits and fails if one of them has no token behind it. It found two on the first
run.

**Why the dialogs looked like a different program.** Because they were one.
`FirstRunDialog` — the first thing anyone ever sees — was an unstyled `QDialog`
with a native title bar, and the delete prompts were `QMessageBox`, which means
a light grey Windows plate with amber text on it, over a black window. There are
now frameless glass dialogs on the same plate as Settings, and one reusable
confirm behind all three prompts rather than three near-copies.

The keyboard behaviour is the part worth explaining. Enter confirms and Escape
cancels, but **focus lands on the safe answer even when it is not the accept
action** — a modal that opens with "Delete" under both the cursor and the Enter
key is a data-loss bug wearing a dialog, and these are reached from a context
menu often enough that the first keypress after one appears is a coin flip. The
destroying answer is the only one that gets red, because colour is the only
warning left once the default has been moved off it. The file and folder pickers
stay native: those are OS chrome, they know where your drives are, and
reimplementing them would be worse in every way that matters.

**And the things that were simply wrong to look at.** The drive strip's pause
button was `rgba(90, 212, 255, 80)` — the one cyan control in an amber
application, now the quiet half of a pair with Go. The workspace browse list
wore the code editor's object name and was therefore setting filenames in the
mono face. Three combo boxes had no object name at all and rendered as bare
transparent chrome beside filled fields. Control heights ran in three tiers —
24, 28 and 34 — and are now two: dock furniture at 28, and the composer, which
is the one row that is not furniture, at 34. Corner radius ran 12, 14, 16 and 18
across floating plates, the notify card and the drop overlay, and is one token
now. The SMS minimize button was wearing the close button's rule and so had a
red hover for an action that is undone by clicking the tray.

The Systems menu was the interesting judgement call. Every row in it is
`setEnabled(False)`, so the menu looked clickable and answered nothing. Making
the rows open the matching Settings tab was tempting and wrong: several of them
name things that are not settings at all, and the menu's job is to report. It
says `status · read only` at the top instead, which is cheaper than inventing a
destination for eight status lines and then having to defend each one.

Not changed: the chat stage keeps its wider gutter, because the extra room is
what the corner ticks sit in and the seam looks right in a screenshot. And
`app_font()` now sizes in pixels rather than points — 10pt is 13.33px against a
stylesheet that says 13px everywhere, which is invisible until a fractional
scale factor rounds the two apart.

Before and after are in `logs/palette/`, captured by `scripts/palette_shots.py`,
which boots the real window offscreen and photographs twelve surfaces so a
colour decision can be looked at rather than read as a diff of hex triples.

## 20. Six places the app offered something it could not deliver

A read-only audit of the wiring layer. None of these crash, which is the whole
reason they lasted: every one is a surface that says yes while the code beneath
it quietly says no.

**An inbound text was being filed somewhere it does not belong.**
`EventType.CHAT_NOTICE` and `Orchestrator.on_chat_notice` wrote inbound SMS into
the conversation archive as a `notice` row, so History would hand it back months
later. Nothing in production ever published that event — the only publisher was
a test — and `test_ui_polish.py` already asserted the opposite, that two arriving
texts leave no notice rows behind. So the archive path was dead code with a
live-looking subscriber pointing the wrong way. The rule the owner actually
wants was never written down anywhere: a text is visible and durable for as long
as the window is open, and gone on the next launch. `SmsChatRegistry` already
behaves exactly like that — `_buffers` outlives the tile, `_forget_window` drops
only the widget — but nothing tested it, so it was one tidy-up away from being
lost. The event, its handler, its subscription and its audit branch are gone, and
`test_sms_chat.py` now pins the shape end to end: a text arrives, the tile is
closed, a second arrives, the tile reopens holding both, and a fresh registry
has nothing. The `notice` role stays in `MemoryStore` — archives written by the
old path still contain those rows, and `ChatPanel` and `recall` still have to
know what one is.

**`inbox_rules` was a setting that only worked in an email nobody reads until
7am.** `world_state._attention_count_part` passed `events=[]`, `mail=[]` and
`inbox_rules=[]` into `collect_attention`, so a user could write a rule about
`billing@`, watch the emailed briefing honour it, and get nothing at all out of
the assistant they were talking to. Both now flow through, but only from what is
already on this machine: the calendar cache the notify poller reads, and the
headers the mail poller last fetched. Nothing on that path opens a socket,
because it runs on every single turn and an IMAP round trip between a question
and its answer is not worth one number. `peek_contact_mail_sync` now keeps
*every* unread header it saw rather than only the ones from known contacts —
inbox rules are written about senders nobody has in a contact book, which is the
point of them — and the cache goes stale after fifteen minutes so a rule cannot
match on a header from an hour ago and call it now. The config comment says
which half is exact and which half lags, because the answer is genuinely
different in the two places and pretending otherwise is how this started.

**Four failures nobody could see.** Each was an `except: pass` on a path someone
was actively waiting on. After an approved workspace write, reading the file
back into the editor was wrapped bare — the write lands, the editor does not
move, and nothing is said, which is the same silent data-surprise as the clobber
bug in item 15; it now says so in chat and names the reason. Calendar loading
and task due-notices in the notify poll could stop entirely with no sign;
they now report, and so does the IMAP peek, which had been reduced to a debug
log while the user sat waiting for email notifications. Those three go through
`_report_poll_state`, which speaks on transitions only: a poller that fails
every thirty seconds and says so every thirty seconds has found a second way to
say nothing, so it reports once, stays quiet, and speaks again when the source
recovers. `peek_contact_mail_sync` raises `MailPeekError` instead of returning
an empty list, because "nobody you know wrote to you" and "IMAP refused the
password" had been the same answer. And `weather` swallowed a failed location
refresh and then reported "no coordinates on file", sending the user to edit a
profile that was never the problem; the refusal now names the refresh failure
that caused it.

**A default that disagreed with itself.** `default.yaml` ships
`tools.image.auto_start: false` and `tools/__init__.py:313` read it with a
fallback of `True`, so anyone whose config omitted the key got Arelis launching
ComfyUI for them — the exact opposite of the documented promise, and the one
place a config default really must not be guessed.

**Image generation was offered to every machine, including the ones that cannot
do it.** The `image` tool and its skill card register unconditionally, so "draw
me a picture" is always on the menu, and on a machine without ComfyUI the first
attempt fails with a message she then has to explain. The `send_email` /
`send_sms` treatment — do not register when unconfigured — does not fit: those
turn on a secrets file that does not change while the app runs, whereas ComfyUI
is a program the owner can start at any moment, and a registry built at launch
would keep saying no for the rest of the session. So availability is reported
rather than guessed. `readiness.py` gains an `image` chip probing
`/system_stats` on the same thirty-second tick as the rest of the strip, the
window parks its answer on `config["_image_ready"]`, and the world-state line
says "image generation needs ComfyUI running" — only when it is not, so she can
offer *once ComfyUI is up* instead of trying and failing. The tool description
carries the prerequisite so the model has the sentence. The chip is not on the
Systems menu yet: `readiness_strip._SYSTEMS_KEYS` needs `"image"` added, and
that file belonged to someone else tonight.

**A voice toggle you could flip that changed nothing.** `VoiceService` reads
`stt_enabled` and `tts_enabled` once, at construction, and only subscribes to
the speech events when speak was on at that moment. Everything after that is a
setting the service never sees: Speak turned on later stays silent, Speak turned
off later still talks, and Listen turned on later answers every utterance with
"voice input is off". The existing warning covered only a cold `VoiceService`
being enabled. `voice_restart_notices` now compares each direction against what
the running service is actually holding and says which one needs the restart and
which way.

New: `tests/test_silent_paths.py` (8), plus regressions in `test_world_state.py`,
`test_sms_chat.py`, `test_history_ui.py`, `test_readiness.py` and
`test_image.py`. Full suite: 1,671 passed, 1 skipped. Smoke run: 17/17 clean.
(`test_orbit_void.py::test_orbit_tokens` fails on an in-flight palette change in
`theme.py`, which is item 19's to settle, not this one's.)

Not done: the world-state attention count still lags the inbox by one mail poll
and goes blank when email notifications are off, which is the price of refusing
to open a socket on the turn path.

## 21. The last of the cross-worker loose ends

Items 19 and 20 were built at the same time, each owning half the files, so each
finished holding a change it could not make. Those are settled here, along with
two things that only showed up once both halves were in the same tree.

`auto_start` now defaults to `False` in `ImageTool.__init__` and
`ensure_comfy_running` as well as at the config read. Starting a program on
someone's machine is not a thing to do by omission, and a default that only holds
because the single caller happens to pass the argument is a trap set for the
second caller.

The Systems menu now lists an `image` chip, the settings voice checkboxes admit
in their tooltips that they need a restart, and the last three colour literals in
`app.py` — the floating-dock stylesheet, the float shell fill, and the window
corner radius — read from the tokens, so the main window is no longer two pixels
rounder than every plate inside it.

One suggestion was declined. Item 19 proposed deleting the four dock object
names, on the evidence that no stylesheet targets them. Nothing does — but
`QMainWindow.saveState()` identifies docks by object name, and that state is what
`layout_store` writes into `ui_layout.ini`. Removing them would have dropped each
dock from the saved layout, so docks would stop returning to where they were
left, noticed days later with nothing pointing back at the cause. The names stay,
with a comment saying what they are actually for and a test that fails if one
goes missing.

Full suite: 1,686 passed, 1 skipped. Smoke run: 17/17 clean.

## 22. Opening it, closing it, and opening it again

Everything in this item is about the ten seconds either side of using Arelis,
which is the part nobody writes tickets about and everybody notices. Four
separate faults, one of them a data risk, and one thing that turned out not to be
a fault at all.

**A black window blinked on every launch.** The desktop shortcut ran
`powershell.exe -NoProfile -WindowStyle Hidden -File run_ui.ps1`, and
`-WindowStyle Hidden` does not mean no window. PowerShell is a console program:
Windows allocates a console, PowerShell starts, and only then does it hide the
window it already has. So the first thing anyone saw of this program was a black
rectangle flashing, which reads as something having gone wrong.

`install_desktop_shortcut.ps1` now targets `pythonw.exe -m arelis` directly.
`pythonw.exe` is a GUI-subsystem binary, so no console is ever created and there
is nothing to hide. The two things `run_ui.ps1` was doing for the shortcut moved
to where they belong: the working directory is a field on the shortcut, and
`QT_QPA_PLATFORM` is now corrected in Python by `force_windows_qt_platform`, which
insists on the real Windows backend for any value but that one. A stray
`offscreen` inherited from a test run is a process that starts, logs normally and
never shows a window, and there is no shell left to clear it. The Windows
installer was already doing this correctly — `arelis.iss` has always pointed at
`{app}\pythonw.exe` — so this was only ever wrong for shortcuts made from a
checkout. An existing `.lnk` does not repair itself; re-running the installer
script rewrites it.

Which exposed a second, worse thing about that script: it always wrote
`Arelis.lnk`, and on a machine with both copies that name belongs to the
installed one. Re-running it from a checkout to fix the flash would have
silently repointed the shortcut used every day at the working tree — a
different data root, so the symptom is not a crash but an Arelis that opens one
morning with none of your history in it. It now writes `Arelis (dev).lnk` when
it can see `pyproject.toml` and `tests/`, the same two markers
`is_source_checkout()` uses, and a wheel cannot carry the second one.

**Clicking the shortcut while Arelis was in the tray did nothing at all.** The
second launch found the single-instance lock held, correctly refused to open a
second window over the same `memory.db`, and then exited without telling anybody
— and the running copy was hidden, so the visible result of double-clicking
Arelis was nothing. The honest response to that is to click it again, which is
exactly what happened.

The plumbing for this existed and was only wired at one end. `activate_existing_ui`
sends `open_ui_request` over the Core↔UI bridge, but with no core running there
was nothing listening on that port. The UI now hosts the server itself whenever it
is not attached to a core, over the same protocol and the same fall-forward ports,
and `IpcServer` gained an `on_open_ui` hook so the process holding the window can
act on the request instead of only passing it on. A core can still only relay it;
a UI is the thing being asked for.

A held lock always means a living process — Windows releases both the named mutex
and the byte lock when a process ends, however it ends, so there is no such thing
here as a stale lock left behind by a crash. That narrows the failure case to one:
a live instance that does not answer. It is retried once after a second and a
half, because a launch arriving two seconds after the last one can reach a copy
that is still building its window, and then it says so in a dialog naming the
notification area and the log file. Nothing kills the other process; it is the one
holding the conversation.

**Two Arelises stacked on top of each other.** This had two causes, and only one
of them was about pixels.

The first was a floating panel left behind. A docked instrument is a child widget
and disappears with its parent, but a floated one is a top-level window in its own
right — `_apply_floating_dock_chrome` gives it `Qt.Window`, where every other
companion surface in the app is a `Qt.Tool` and is therefore hidden by Qt along
with its parent. So closing to the tray left the panel on the desktop with nothing
behind it, and the next launch painted a whole new glass underneath an orphan
still sitting on top. Measured, before the fix: with the glass in the tray, one
visible top-level window remained, titled `thinking`. Floating docks are now
parked when the glass leaves the screen and brought back when it returns, on the
close-to-tray path and on minimize, which is the other way to take a window off
screen. Parked rather than closed, because coming back to a different set of
instruments than you left would be its own small betrayal, and the View menu is
told to ignore it so the checkmarks do not lie.

The second was the window coming back the wrong size. `show_from_tray` called
`showNormal()`, which answers "not maximized" whatever the window had been, so
restoring a maximized glass presented the full-screen frame Windows had kept and
then resized it down over the top. The state is now recorded on the way out —
minus Minimized, since nobody asking for the window wants it back in the taskbar
— and applied before the window is shown, so it is mapped once and at its final
size. `invalidate_window_surface` then marks the whole layered surface dirty:
Qt flushes only the region it believes changed, which on a re-show is nothing, so
the parts Qt has no reason to touch are the parts that keep the old picture.
Deliberately without `RDW_UPDATENOW`, which would paint synchronously into a
window Qt is still mapping.

Fixing a maximized restore also exposed a launch-blocking crash worth naming.
Restoring a saved maximized layout calls `setWindowState` from inside the window
constructor, and the resulting state-change reached `_sync_notify_surface` before
the mailbox windows existed. That raised `AttributeError`, which `run_ui` reports
as "Arelis window failed to start" — so a maximized glass closed one evening could
refuse to open at all the next.

**The event loop was being switched off with work still running in it.** A clean
tray Quit ended with `quit_end_ms=134`, then `Task was destroyed but it is
pending` for `EventBus.run` and `MemoryIndexer.run_batch`, and then, two and a
half seconds after quit had finished, `Indexed 3 workspace file(s) into memory`.

That last line is the part that mattered. The indexer does its writing inside
`asyncio.to_thread`, so stopping the loop abandons the *await* while the worker
thread carries on into `memory.db` with the interpreter shutting down around it. A
process exiting during a SQLite write is how an archive of every conversation
someone has had becomes a file that no longer opens. Nothing had broken yet.

`_drain_event_loop` now runs before the loop stops, in a deliberate order: cancel,
so nothing new starts; wait for the cancellations to land, so tasks unwind through
their own `finally` blocks; then wait on the thread pool, which is the only way to
know the last statement has been written rather than merely that nobody is waiting
for it; then async generators, because closing those can await. Tray Quit gets a
tighter ceiling than an ordinary close, the same distinction `closeEvent` already
draws, and in practice the work is already finished so it costs nothing.

The first version of this used `asyncio.wait_for` and was worse than what it
replaced. `wait_for` cancels what it is waiting on and then waits for that
cancellation to complete, so a task which swallows `CancelledError` — a bare
`except Exception` around an await is enough — turned the ceiling into a hang, and
Quit would never have returned. It was `asyncio.wait` all along. A test that
builds exactly such a task is what caught it, after wedging a test run for half an
hour first.

**And one finding that is not a bug.** Every launch shows two `python` processes
in Task Manager, and this is normal. Python on this machine is installed through
the new install manager, where the interpreter that gets launched is a small
redirector that starts the real runtime as a child process and waits for it. It
happens for `python -c "import time; time.sleep(25)"` with nothing imported at
all, and for every other Python program on the machine. Measured: the parent uses
about 3 MB and does nothing; the child is the actual Arelis. Nothing in this
program spawns it, there is nothing to fix, and it is not a leak. A packaged
install does not show it, because the installed `pythonw.exe` is a real
interpreter rather than a redirector.

Full suite: 1,708 passed, 1 skipped. Smoke run: 17/17 clean.
